# NAO capture integration (prototype)

This document describes the current **PC-side** contract. It does not
modify the speech, computer-vision, or Choregraphe scenario modules.

## Current data identifiers

- A session is created using `POST /api/session/start`.
- Each scenario uses the stable `scenario_id` from `data/scenarios.json`
  (1 Happy, 2 Sad, 3 Angry, 4 Neutral).
- Start the scenario with `POST /api/scenario/start` using both IDs.
- Audio and images can arrive in either order. The backend stores them
  under the same session and scenario.

Canonical backend file paths (generated by the server, not by the robot):

```text
data/session_audio/<session_id>/scenario_<scenario_id>_<unique>.wav
data/session_frames/<session_id>/scenario_<scenario_id>_<unique>.jpg
```

Captures and `data/sessions.json` are excluded from Git.

## Standard way to upload existing local captures

Keep FastAPI and Ollama running. First create a session and start scenario 1
in Swagger at http://127.0.0.1:8000/docs. Then run from project root:

```powershell
python -m backend.nao_transfer --session-id YOUR_ID --scenario-id 1 --audio "data/laptop_audio/example.wav" --image "data/nao_frames/example.jpg"
```

You can specify `--image` more than once. You can send just audio or just
images; repeating the command is permitted when a capture arrives later.
The bridge checks that this scenario is active before posting anything.
The FastAPI server generates the canonical filenames.

## Fetch captures from a physical NAO (after verifying remote files exist)

```powershell
python -m backend.nao_transfer --session-id YOUR_ID --scenario-id 1 --nao-audio
```

The current committed Choregraphe `Capture_Audio` box records
`/home/nao/response.wav`. Override with `--remote-audio-path` if the
installed behavior writes elsewhere, and with `--nao-ip` if necessary.

For a *confirmed actual still file* on the robot you can additionally use
`--remote-image /home/nao/recordings/cameras/your_photo.jpg`.
Do not assume that a file exists there: the current
`Capture_Camera` Choregraphe example sends raw RGB over HTTP directly
to `/api/camera/raw-frame`, which currently does **not** assign
session/scenario IDs. Connecting that camera behavior to the session-aware
endpoint remains pending integration with the scenario team.

**Do not run the old `backend/watch.py` at the same time as the new
session-aware transfer bridge.** The old watcher is retained as a legacy
data-acquisition tool and does not attach session/scenario IDs.

## Scenario lifecycle and recoverable errors

An ordinary flow is:

```text
POST /api/session/start
POST /api/scenario/start
POST /api/camera/session-frame (optional, any order)
POST /api/audio/evaluate (or /api/response/submit for text tests)
POST /api/scenario/complete
[repeat for other scenarios]
POST /api/session/end
```

If there was no response, or processing failed, the active scenario can
be retried or skipped using:

```json
{
  "session_id": "YOUR_ID",
  "scenario_id": 1,
  "action": "skip",
  "reason": "no_response"
}
```

Submit this to `POST /api/scenario/recovery`. Set `action` to `retry`
if another recording attempt is planned. Supported reasons are
`no_response`, `no_speech_recognized`, `transcription_failed`,
and `processing_failed`.

A skipped scenario does not create a verbal result and **is not
Incorrect or Unclear**. Recoverable Whisper/Qwen failures are logged in
the scenario progress record. `GET /api/session/{id}` exposes
`scenario_progress` and `skipped_scenarios`.

The session-ending statuses are:
- `completed`: all scenarios completed with saved verbal results
- `completed_with_skips`: all scenarios resolved, at least one skipped
- `ended_early`: some scenarios were never completed or skipped

## Run the automated tests

```powershell
python -m unittest tests.test_backend_workflow -v
```

Tests mock Whisper, Qwen, file uploads, and the network. Do **not** use a
broad test-discovery pattern that also runs `tests/test_microphone.py`
and `tests/test_camera.py`: those are manual hardware demos.
